# SCENE3D_PIPELINE.md — 現場3Dビュー生成パイプライン（S3D-1〜S3D-3）

工事計画パイプライン（CONSTRUCTION_PLAN_GENERATION.md）と同じ流儀で、現場3Dビューの
生成を「入力 → 展開 → 検証 → 描画」の純関数パイプラインとして形式化する。
計画が「いつ・何をするか（タスク）」を決め、本パイプラインが「いつ・どこで・何が・
どう動いて現れるか（配置イベント列）」に展開し、レンダラはそれを時刻 t で描くだけにする。

- 実装: `model/scene_expand.py`（S3D-1 展開エンジン）／ `model/scene_validate.py`（S3D-2 検証）
- 規則: `model/scene_rules.json`（展開規則テーブル。コードは実行エンジンだけ）
- 出力: `model/generated_scene3d_<物件stem>.json`（ScenePlan、スキーマ `scene3d/1.0`）
- 描写原則の正: `3D_VIEW_SPEC.md` §3（部材は1つずつ現れる／フェード・グラデーション出現の禁止／
  節単位の建方／打設フロント／足場JIT／天井裏の順序）。生成方法の正は本書。

## 1. 決定の記録（ユーザー承認済み、2026-11-10）

| # | 決定 | 内容 |
|---|---|---|
| D3D-1 | 入力は固定2点 | 建物モデル v0.7 JSON と ConstructionPlan JSON を正入力とする。付随入力（計画詳細・ゲーム換算・設備推論・CP-0）は検証・換算の参照にのみ使う |
| D3D-2 | 3段分離 | S3D-1 描画キュー展開 → S3D-2 検証（SVルール）→ S3D-3 レンダラ。レンダラは生成ロジックを持たない（§6 契約） |
| D3D-3 | 部材粒度＝全数 | 柱・梁・杭・基礎・外壁・建具は1つずつ部材化する。面状施工と対配管のみ施工実態単位で集約する（§3.4） |
| D3D-4 | 規則はデータ、コードはエンジン | タスク種別ごとの展開規則は `scene_rules.json` に置く。規則に無い系統は発明せず gap として登録する |
| D3D-5 | 動きもイベント列に含める | 搬入→揚重→（横引き）→建込み、重機・人物の移動、高所作業車の階別搬入出までをイベントとして持つ |
| D3D-6 | 純関数・決定性 | 全段は (入力, シード) の純関数。乱数と現在時刻の持ち込み禁止。同じ入力からは同一ハッシュの出力が再生成される（SV-04） |
| D3D-7 | 直すのは入力側 | 検証で落ちたら生成物ではなく入力・展開規則・エンジンを直す。権威順位: ユーザーの実務訂正 ＞ 調査 ＞ 外部素材 |

## 2. 入力仕様

| 入力 | ファイル | 役割 |
|---|---|---|
| 建物モデル v0.7 | `model/generated_game_mall.json` / `generated_commercial_seeded2.json` / `generated_commercial_seeded2_kameari.json` | 幾何の正（軸・階平面・コア・シャフト・壁・開口・敷地） |
| ConstructionPlan | `model/generated_construction_plan_<stem>.json` | タスク・期間（es/ef）・依存・シードの正 |
| ゲーム換算 | `model/integration/generated_game_schedule_<stem>.json` | 実日数→ゲーム日換算（DP-1: 換算は integration 層の結果を受け、ここでは再換算しない） |
| 設備推論 | `model/generated_equipment_<stem>.json` | 天井裏・幹線のラン（シャフト→室）の正 |
| CP-0 数量 | `model/generated_plan_cp0_<stem>.json` | 検証時の突合せ（1F柱本数） |
| 展開規則 | `model/scene_rules.json` | タスク種別ごとの展開規則・許容値・集約方針 |

stem の対応付け: 建物ファイル名から `generated_` を除いたものが計画側の stem。
出力の `meta.inputHashes` に全入力ファイルの SHA-256 を刻む。

### 2.1 エンジンが入力から導出する幾何（再計算規則）

- **柱位置**: 構造軸交点のうち、隣接4セルの少なくとも1つがその階の平面にあり、
  4セル全てが柱フリーゾーンではなく、columnExceptions に当該階が無い点（CP-0 の
  `quantities.columnCount1F` と完全一致することを SV-06 で担保）。
- **大梁区間**: 構造スパンごとに、スパン内の全単位セルについて実スラブ片（その階の
  solid セル、屋根は屋根セル）が少なくとも片側にある場合のみ梁を置く
  （Phase 0 の大梁クリップ規則。「なぞの板」回帰の恒久対策）。
- **節（セクション）**: 計画のデッキタスク `frm-sN-<階>-d` から節→階の対応を復元する。
- **クレーンステーション**: 建物平面 bbox の外周 7m に、長辺方向 30m 間隔で配置（＋東西中点）。
- **設備ラン経路**: シャフト中心→対象室中心の経路候補（X先行／Y先行／工区中心経由）を
  決定的順序で試し、その階の実平面（footprint − 吹抜け）に収まる最初の候補を採用。
  吹抜けを渡らざるを得ないランは `pathViaVoid` として数える（発明で迂回しない）。

## 3. S3D-1 描画キュー展開（scene_expand.py）

### 3.1 段取り

1. 入力5点＋規則を読み、ハッシュを記録する。
2. §2.1 の幾何インデックスを構築する。
3. 計画タスクを (es, ef, id) 順に走査し、`scene_rules.json` の `taskKinds` の
   `idRegex` に最初に一致した規則の生成器を適用する（規則は計画タスク分類に対応付け済み）。
   一致しないタスクは `stats.unmatchedTasks` に残る（現行3物件では 0 件）。
4. 生成器は部材（members）とイベント（events）を決定的な順序で追加する。
   部材 id・イベント id は生成順の連番（`m-000001` / `e-000001`）。
5. イベントを (t, id) で並べ替え、統計と contentHash を計算して書き出す。

### 3.2 時刻の扱い

- イベントの `t` は実働日（小数）。タスク内位置 `u`（0〜1）から `t = es + u×(ef − es)`。
- `g` はゲーム日（小数・0始まり）。integration 層の換算結果から
  `g = (gameStart − 1) + u×(gameEnd − (gameStart − 1))` で受ける（再換算しない、DP-1）。

### 3.3 展開規則（scene_rules.json / taskKinds）

タスク種別ごとに「どの部材が・どの順で・誰が（班／重機）・どう動いて現れるか」を記述する。
カバー系統: 着工準備／土工事（山留め・掘削・捨てコン＋地下ピット）／杭（試験杭・本杭・杭頭処理）／
基礎（型枠・配筋→打設→解体・埋戻し）／鉄骨節（柱→大梁→ブレース→本締め色替え相当の state）／
デッキ・床（配筋束→マット→打設フロント→養生）／屋上（パラペット→防水→保護→ドレン通水確認）／
外装（面×階レーン、足場JIT組立→パネル→サッシ→シーリング→足場解体）／電気（引込・キュービクル揚重・
幹線立管）／検査チェーン（書類・申請は action、実施は inspect、受電は gate）／高所作業車の階別搬入出／
工区内装（墨出し→LGS→PS縦管→支持材→ダクト・冷媒→衛生配管→電気ラック→天井下地・ボード→
設備2次→仕上げ→床→建具→器具付け→美装）／EV単線（レール→かご・巻上機→試運転→養生・工事用解放）／
外構4セクター（埋設→路盤→舗装→植栽・ライン）／引渡し（仮設撤去→gate）。
各規則に basis（rule/inferred/default/gap）と出典を持つ。

鉄骨部材（柱・大梁）の標準動作列: `stock`（トラック搬入→自位置前面に仮置き）→
`lift`（最寄りステーションから揚重）→ 届かない場合は着地点までの `lift` ＋ `carry`（横引き・台車）
→ `place`（建込み）。クレーン計画は計画側の工法選択（ラフタークレーン＋横引き、
タワークレーン不採用）を前提とし、ステーション間隔・到達距離は規則の `global` に置く。

### 3.4 集約方針（aggregation）

全数が原則。次だけは施工実態の単位に集約し、出現順序（フロントの進行）は保持する。
根拠は `scene_rules.json` の `aggregation` に記録。

- 行ラン集約: 掘削底・捨てコン・防水シート・保護コンクリート（帯／ロールで進む面）
- 構造ベイ集約: デッキプレート・配筋マット・土間（構造スパン単位。配筋本数は `bars` に保持）
- ペア集約: 冷媒管（液管＋ガス管を1式、`pair: true`）

### 3.5 ScenePlan スキーマ（scene3d/1.0）

```
meta     : { generator, building, buildingId, seed, difficulty,
             inputFiles, inputHashes, rulesVersion, cranePlan, contentHash }
timeAxis : { totalRealDays, totalGameDays, durationScale, note }
actors[] : { id, kind, boxes, faces, label }   # 班・重機・検査員・高所作業車
members[]: { id, kind, task, box{x,y,z,dx,dy,dz}, faces, basis,
             level?, zone?, bars?, pair? }      # 座標は m、box は最小隅
events[] : { id, type, task, u, t, g, member? / members? / actor?,
             at?, via?, state?, note? }
stats    : { memberCount, eventCount, actorCount, faceEstimate*,
             tasksMatched/tasksTotal, unmatchedTasks, skippedRuns,
             skippedBraces, pathViaVoid, pathFallback, columnPositionsL1 }
gaps[]   : { kind, status: "gap", note }
```

イベント種別:

| type | 意味 |
|---|---|
| stock | 搬入・仮置き（部材が敷地内に現れる） |
| lift | クレーン揚重（at = 揚重先） |
| carry | 横引き（via = 着地点、at = 最終位置） |
| place | 配置・建込み（部材が最終位置に現れる） |
| state | 状態変化（本締め・打設・養生・仕上げ・試運転調整 等） |
| remove | 撤去・搬出（足場解体・仮設撤去・配筋束の消費 等） |
| move | アクター（重機・AWP・かご）の移動 |
| work | 班の作業（位置と担当班を伴う） |
| action | 書類作成・墨出し・美装など部材を伴わない作業 |
| inspect | 検査の実施（検査員アクターを伴う） |
| gate | ゲート成立（受電・引渡し） |

部材の出現は place（材料は stock）でのみ起こる。フェード・スケールイン等の
「徐々に現れる」表現はスキーマに存在しない（レンダラ契約 §6 でも禁止）。

## 4. S3D-2 検証（scene_validate.py、SVルール）

検証は生成物ではなく入力から幾何を独立に再計算して照合する。独立に実行できる:

```
python3 scene_validate.py                 # 3物件まとめて
python3 scene_validate.py <建物モデル>    # 1物件
```

| # | 検査 | 内容 |
|---|---|---|
| SV-01 | 支持・突出 | 全配置部材のはみ出しを種別ごとの領域（実スラブ片・シャフト矩形・実効敷地）と許容値（rules の tolerancesM）で判定。「なぞの板」回帰チェック。未分類の種別は自動的に FAIL。仮囲い・ゲート（tempFence/tempGate）に限っては実効敷地の回避を使わず、実ポリゴンでの内包判定＋建物フットプリント（L1セル群）と交差したら FAIL のハードゲートで判定する（2026-11-11 追加） |
| SV-02 | 出現順序 | 外装・内装部材のタスク開始が躯体完了（frm-* の最大 ef）以降であること。天井ボードが同工区の隠蔽設備（ダクト・配管・ラック・冷媒）の配置完了後であること |
| SV-03 | 時刻・参照 | 全イベントの u∈[0,1]、t がタスク期間内、g がゲーム換算期間内。参照する部材・アクターの存在。全数部材に出現イベント（place/stock）があること |
| SV-04 | 決定性 | 展開を2回再実行し、contentHash が相互に一致し、ファイルの刻印とも一致すること |
| SV-05 | 面数予算 | 全体表示の不透明面見積もりが予算（最大物件 100,000 面）以内。面数は描画階層（§5）で数え、全詳細の合計も併記する |
| SV-06 | 柱本数突合 | 1F柱位置の数が CP-0 の columnCount1F と一致すること |
| SV-07 | クレーン計画 | 柱・大梁の全数が「最寄りステーションから到達距離内」または「横引きイベントあり」を満たすこと。タワークレーン不採用・ラフター基準が計画に記録されていること |

敷地ポリゴンが建物平面を包まない物件（placeholder の既知制限）では、SV-01 の敷地判定を
実効敷地（ポリゴン ∪ 平面）で行い、警告として明示する。ただし仮囲い・ゲートだけは
この回避の対象外（上表のハードゲート）。基礎部材の支持の本体は
「中心が柱位置と一致すること」で担保し、型枠のはみ出しは余掘り相当を tolerancesM に置く。
亀有は 2026-11-11 の是正で実効敷地ポリゴンが平面を包むようになり、現在この警告を
出す物件は無い（是正の経緯は §8）。

## 5. 描画階層と面数

3D_VIEW_SPEC §3.9 の段階描画に基づく。全体表示では天井裏はダクト＋ラックのみとし、
内装・天井裏の詳細部材（rules の `viewTiers.detailKinds`）は階単独表示／カットアウェイで描く。
SV-05 の予算は全体表示の見積もりに適用する。

## 6. S3D-3 レンダラ契約

- レンダラは ScenePlan を入力とし、時刻 t（または g）におけるシーン状態を描くだけである。
  生成ロジック（配置計算・順序決定・経路選択）をレンダラ側に持ち込まない。
- 状態の復元: イベント列を時刻順に適用する。部材は place/stock で現れ、remove で消え、
  state で状態（色・属性）が変わる。アクターは move/lift の at へ移動する。
- 時刻換算: 実日数→ゲーム日の換算は integration 層の結果（イベントの `g`）を使う。
  レンダラは換算を再計算しない（DP-1）。
- 描画原則（3D_VIEW_SPEC §3 が正）: 部材は離散的に現れる。フェード・グラデーション・
  スケールインによる出現は禁止。面は両面・不透明を基本とし、同一平面の重なりは
  仕上げ＞下地＞構造の優先で避ける。
- 面数: 全体表示は SV-05 の見積もり以内を前提とする。詳細階層の部材は表示モードに
  応じて出し分ける（§5）。
