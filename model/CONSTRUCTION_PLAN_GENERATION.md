# 工事計画生成ロジック 形式化 v1.1（確定版）

作成：2026-11-10。同日に未決定 DP-1〜DP-5 を推奨案どおりで確定し v1.0 とした（ユーザー決定 2026-11-10、§8 に決定記録）。同日、DP-3（難易度はユーザーが 簡単／普通／難しい を選ぶだけ、実値はシード抽選）と DP-4（L3はゲームではスキップ）をユーザー訂正で差し替えて v1.1 とした。位置づけ：物件生成ロジック（`BUILDING_MODEL_SCHEMA.md` v0.7、`generate_building.py`）が生成した**設計レベルの建物モデル**を入力とし、ゲームの施工フェーズが従う**大筋の工事計画（施工計画）**を生成するロジックの形式化。施工中の変更・立て直しは本書の対象外で、計画は「基準線（ベースライン）」として生成し、変更は施工側（WORK_STRUCTURE_V2、夕礼・明日の段取り、挽回計画）が担う。

根拠：`~/workspace/research_notes/japan-construction-planning-research-20261109-1904/report.md`（日本の施工計画の詳細調査。一次資料中心）。本書の記述は原則として (実務)＝調査で裏付けた実務、(決定)＝本プロジェクトでの決定、(推定)＝ゲーム用に置いた仮定、を区別する。ユーザーの実務訂正は調査より優先する（DOCUMENTS.md の優先順位どおり）。

---

## 0. 要旨（決定事項）

1. **(決定) 工期と工事金額は入力ではなく導出値である。** 建物モデル→数量→（歩掛×投入数で日数化／単価で金額化）という1本の数量モデルから両方を出す。延床面積→工期の公表公式は存在しない（実務）。㎡単価法と工期率は検算専用。
2. **(決定) 計画の完成は様式ではなく検証で判定する。** 建物モデルの V ルールに対応する計画検証 **PL-01〜PL-12**（§4）を全て満たしたとき「計画完了」。未達は警告ではなく未完了として扱う（特に検査ゲート PL-06 は引渡しの普遍条件と連動）。
3. **(決定) 全ての計画要素に根拠タグを持たせる。** 建物モデルの `assumptions` と同型に、各決定を `rule`（法定・標準仕様・確定ルール）／`inferred`（推論ルール）／`default`（ゲーム既定）／`player`（プレイヤー・所長の判断）／`gap`（未定）で記録する。推論で補うこと自体は正とし、事実と混ぜない。
4. **(決定) 生成は3層に分ける。** A＝自動生成（機械的）、B＝推論ルール（候補生成＋スコアリング＋初期値）、C＝人の判断（ゲームではプレイヤーの意思決定として残す）。C を自動で潰さない。
5. **(決定) 出力は実務の二層構造に対応させる。** ゲーム開始時に生成するのは総合施工計画に相当する `ConstructionPlan`（全体）。工種別計画は各工種の着手前に詳細化する遅延生成とし、開始時に全量を作らない（実務の提出時期と同じ）。

## 1. 入力

### 1.1 建物モデルから読むもの（既存フィールド → 計画での使い先）

| 建物モデルの入力 | 主なフィールド | 計画での使い先 |
|---|---|---|
| 建物概要 | `Building.use / structure / floors / outline.*`（用途・構造・階数・延床・建築面積・高さ） | 工事概要（PL-01）、工法テンプレート選択、数量の総量検算、㎡単価照合 |
| 仕様シード | `seedSpec.*`（structureSystem / frameMethod / foundationType / exteriorWall / roofUse / roofSpec / ceilingHeightMm / sprinkler / parking）＋ `outline / zoning / systems` | 工法選定の確定値（値があれば推論より優先、建物モデル V24 と同じ原則）。法規条件は検査・区画、設備概要は EquipmentRun 生成と受電・試運転計画の入力 |
| 構造推論 | `structure.*`（system / columnSizeMm / girderDepthMm / seismicElements / columnFreeZones / groundAssumption / constructionDerived） | 躯体サイクル・節の構成、鉄骨量・コンクリート量の推定、地盤仮定→山留め・杭・バッファの初期値。`constructionDerived.frameCycle / crane` は計画側で再導出して照合する |
| グリッド・階 | `Grid.axes / structuralAxes / span`、`Level.*`（階高・プレート） | 工区割（工区境は芯上、建物モデル V7 と同規則）、型枠転用・打設量、揚重の届きと横引き距離 |
| 部材 | `Column / Beam / Slab / Wall(+openings role) / Core / Shaft / Foundation / Roof / CurtainWall / Covering / Reinforcement` | 数量エンジン（§5.1）の直接入力。部材IDがそのまま作業・検査・写真の対象IDになる（建物モデル §7 の接続を継承） |
| 室・区画 | `Room.*`（用途・面積・zoneId）、`Zone.*`、`Compartment.*`（防火区画） | 仕上WBSの分解単位、消防・完了検査の区画対応、テナント／共用部の区別 |
| 設備 | `EquipmentRun.*`（生成済みの場合）、`Shaft(PS/DS/EPS/EV)`、`systems.*` | 設備3系統×3段階の作業生成。**既知の不足：シード生成では EquipmentRun 未生成（gap）** → §5.4 の系統テンプレートで推論生成し `inferred` と明示する |
| 敷地 | `Site.polygon / roads / gates / neighbors` | 仮設計画（ゲート・搬入経路・仮囲い・置場候補）、近隣リスクフラグ、搬入制約。シードで未調査の敷地周辺は `gap` のまま計画側でも引き継ぎ、既定値で埋めた場合は `default` と記録 |
| 前提記録 | `assumptions[]`（seed / inference / default / gap） | 計画要素の根拠タグへ継承。建物側が `gap` の項目に依存する計画要素は自動的に `gap` または `inferred` になる（格上げ禁止） |

### 1.2 建物モデル以外の入力（計画生成パラメータ）

| パラメータ | 内容 | 既定（決定） |
|---|---|---|
| `calendarProfile` | 稼働暦：閉所パターン、祝日、長期休暇 | ゲーム開始時は **4週8閉所**（ユーザー確定 2026-11-09、本編の閉所パラメータと同一）。悪化段階（6閉所→4閉所→閉所なし）は施工中の変更であり初期計画には使わない |
| `weatherProfile` | 地域×季節の作業不能日（雨・台風・冬期）と工種別感度 | 関東・通年を既定。日建連方式（過去実績から都道府県別に雨天・台風を設定）が実務の見本 (実務) |
| `durationScale` | 実工期→ゲーム日数への換算率 | **（決定 DP-1）計画内部は実日数で保持し、換算は表示・進行層で行う** |
| `costTables` | 歩掛テーブル、単価テーブル（複合単価・市場単価相当）、共通費率 | **（決定 DP-2）工種別の標準テーブルをゲーム用に1式新規作成する**。有料刊行物（建築コスト情報等）の数値は取り込まない |
| `companyPolicy` | 本社・支店の政策：目標粗利率、実行予算の査定方針 | 標準粗利率は実務に存在しないため数値は置かず、パラメータとして外から与える (実務)。未指定なら実行予算は「積み上げ原価そのもの＋要査定フラグ」で出す。ゲームでは実値を難易度レンジからのシード抽選で決める（DP-3） |
| `difficulty` | **（決定 DP-3、2026-11-10 訂正）難易度：簡単／普通／難しい** | **ユーザーが決めるのはこの3択だけ**。C層の実値（バッファ率、実行予算の査定率、歩掛・単価の揺れ、工法選定の保守性 等）は難易度ごとのレンジから `seed` で抽選して決め、`decisions` に抽選結果と根拠タグを記録する。個別項目の確認画面は置かない |
| `seed` | 生成の乱数種 | 建物生成と同一シードから派生させ、同じ物件・同じ難易度では同じ計画の揺れを再現可能にする。DP-3 の実値抽選にもこのシードを使う |

## 2. 出力：ConstructionPlan（完了条件としてのアウトプット）

実務の総合施工計画書16項目（調査 問い2）を、ゲームが消費できる形に写したもの。各ブロックに「完了の判定」を持つ。

| # | ブロック | 内容（データとして持つもの） | 実務対応 | 完了の判定 |
|---|---|---|---|---|
| 1 | `overview` 工事概要 | 建物モデルからの転記スナップショット＋工期・金額の導出値（§5）への参照 | 16項目-1 | 建物モデルと全項目一致（PL-01） |
| 2 | `premises` 前提推論 | 推定工期（準備／本体CP／後片付けの内訳、低・基準・高の3点）、推定工事価格（工種別直接費＋共通費の内訳）、請負金額相当、実行予算、工期率・㎡単価の照合結果 | 工期設定の基本的考え方／積算基準 | 3点推定と照合警告が揃う（PL-09, PL-10） |
| 3 | `tasks` 作業ネットワーク | WBS作業の一覧：{id, 工種, 工区・階・対象部材ID, 数量・単位, 日数の根拠式, 先行関係（種別＋ラグ）, 資源, ゲート, 天候感度, 原価} | 実施工程表の論理側 | 閉合・非循環・引渡し到達（PL-02）、全作業に日数根拠（PL-04） |
| 4 | `schedules` 工程表階層 | 全体工程（マスター、CPとマイルストーン付き）、出来高曲線（計画Sカーブ）、3ヶ月工程の初回窓の骨格。1ヶ月・週間は施工中のローリング生成（本書対象外） | 工程表の階層（調査 2.5） | 全体が暦展開済みで `premises` の工期と一致（PL-05） |
| 5 | `methods` 工法選定記録 | 工種ごとの候補・比較スコア・採用工法・根拠タグ（山留め／杭／躯体／打設／揚重／足場／外装 等） | 主要工種・施工方法、工法比較表 | 主要工種に未選定がない（`gap` が残る場合は計画は暫定完了どまり、§4.2） |
| 6 | `temporaryWorks` 仮設計画 | 段階別（準備／土工・基礎／躯体／仕上・外構）の配置：仮囲い・ゲート・事務所・詰所・トイレ・置場スポット割当・搬入動線・仮設電気水道・足場（面別）・揚重機（機種・位置・能力照合） | 総合仮設計画図 | 各段階の配置が当該段階の作業を覆い、揚重能力照合を通過（PL-07, PL-11） |
| 7 | `resources` 資源計画 | 職種別労務の山（期間別人数）、重機・仮設材の手配時期、協力業者一覧（工種・入場予定・班規模の初期値） | 現場組織・施工体系と連動 | 山の集計が `tasks` と一致。ピーク競合は警告として列挙（PL-08） |
| 8 | `procurement` 調達・製作計画 | 長納期品目（鉄骨／カーテンウォール／建具／EV／キュービクル・受変電／空調機器 等）の {製作図提出→承諾→発注→製作→工場検査→搬入} 日程 | 調達・製作計画 | 全品目の搬入日が使用作業の開始に間に合う（PL-02 の一部として検証） |
| 9 | `inspections` 検査・申請・協議計画 | 検査チェーン（書類作成→申請・依頼→実施）の全件：{対象, 実施者・立会者, リードタイム, 必要証拠（写真カテゴリ・試験）, ゲート先}。法定（中間・完了・消防・EV）、受電、官庁・インフラ協議の一覧 | 検査・試験計画 | 隠蔽部は全て「閉じる作業」の前に検査が置かれる（PL-06） |
| 10 | `qcdsePlans` QCDSE管理計画 | Q：品質管理表（一工程の確認段階・基準値・写真計画）／ C：原価内訳と月別出来高計画／ D：フォローアップ規則（乖離時の是正トリガ）／ S：重点危険作業・作業主任者・届出／ E：騒音振動・産廃フロー・近隣対策 | 品質計画（承諾対象）・安全管理・環境対策・廃棄物処理計画 | 数値基準のない管理表は未完成（PL-06 と併せて判定） |
| 11 | `risks` リスク・バッファ計画 | リスク一覧 {事象, 発生条件（モデル由来フラグ）, 影響先タスク, バッファ（期間・費用）の置き場所, 監視指標} | リスク検討（調査 S10） | モデル由来フラグ（軟弱地盤・狭小敷地・近接隣地 等）が全件リスク化されている |
| 12 | `decisions` 判断記録 | C層の判断の一覧：{論点, 選択肢, 採用, 決定者（player/system-default）, 根拠タグ} と未定リスト `undecided[]` | 基本方針・VE | 未定が空、または暫定完了として明示（§4.2） |

## 3. 生成手順（パイプライン）

実務の S1〜S13（調査 問い3）を、入力が建物モデルである前提に写し替えた **CP-0〜CP-10**。各段の「機械／推論／判断」は A／B／C 層に対応する。

| 段 | 処理 | 入力 → 出力 | 層 |
|---|---|---|---|
| CP-0 | **前提推論**：数量エンジンで工種別・工区別数量を算出し、工期3点推定と金額推定を行う（§5） | 建物モデル → `premises` の初版、数量表 | A（数量・計算）＋B（原単位の選択） |
| CP-1 | **照査**：建物モデルの `assumptions` の `gap` と相互不整合（例：EquipmentRun 未生成、敷地周辺未調査）を洗い出し、計画側の不足リストにする。不足は推論で補うか `gap` として残すかを項目ごとに決める | 建物モデル → 不足リスト、補完方針 | A＋B |
| CP-2 | **現場条件の確定**：敷地・接道・隣地・地盤仮定を読み、搬入制約・近隣感度・地盤リスクのフラグを立てる。実務の現地調査に相当し、ゲームではモデル＋ `default` 推論で代行する（根拠タグ必須） | Site＋groundAssumption → 制約条件リスト | B |
| CP-3 | **基本方針**：順打ち等の施工方針、QCDSEの重点、工区分けの考え方。ゲームでは方針の実値を難易度レンジからのシード抽選で決める（DP-3）。ユーザーの入力は難易度選択のみで、抽選結果は `decisions` に記録される | CP-0〜2＋`difficulty`＋`seed` → 方針レコード | C（実値はシード抽選） |
| CP-4 | **工法・仮設選定**：§6 の推論ルールで候補を生成し工期・原価・安全・近隣影響でスコアリング、初期採用を決める。揚重は確定ルール（ラフター＋横引き原則、タワーは最大1基・基礎完了後・盛替えは有償）をハード制約として適用 | CP-0数量＋CP-2制約 → `methods`、`temporaryWorks` 初版 | B（制約は A） |
| CP-5 | **WBS生成**：構造×工法×用途で選んだ工程テンプレート（WORK_STRUCTURE_V2 が S造商業の実体）を建物に展開する。工区割は Zone をそのまま使い、設備は3系統×3段階、検査はチェーンとして生成する（§6.3） | テンプレート＋建物モデル → `tasks`（依存関係まで） | A＋B（テンプレート選択） |
| CP-6 | **日数・原価の確定計算**：各作業の日数＝数量÷（歩掛×投入数）（固定日数型は養生・検査・製作の根拠を別に持つ）、原価＝数量×単価。CP-0 の概算を作業単位の積み上げで置き換える | 数量・歩掛・単価 → 日数・原価つき `tasks` | A |
| CP-7 | **ネットワークと暦**：CP計算でクリティカルパスとフロートを出し、`calendarProfile`＋`weatherProfile` で暦展開。資源の山積みを集計し、フロート範囲内の開始シフトで山崩し案を作る | `tasks`＋暦 → `schedules`、資源の山 | A（山崩し案は B） |
| CP-8 | **調達・検査チェーン生成**：§7 のリードタイム表から調達日程と検査チェーンを生成し、`tasks` に接続する。受電・概成・総合試運転をマイルストーン化する | リードタイム表＋`tasks` → `procurement`、`inspections` | A＋B |
| CP-9 | **QCDSE管理計画とリスク**：品質管理表（対象部材→確認段階→基準値→写真カテゴリ）、安全重点（工種×段階から）、環境・産廃、リスク・バッファ配置を生成する | CP-4〜8 → `qcdsePlans`、`risks` | B（基準値引用は A） |
| CP-10 | **検証と確定**：PL-01〜PL-12 を実行。未達は該当段へ差し戻す。工期率・㎡単価の照合警告を `premises` に記録し、計画の完了レベル（§4.2）を付けて出力する | 全ブロック → `ConstructionPlan`（版付き） | A |

差し戻しの原則（決定）：検証で落ちたら計画データを直接編集せず、**該当段の入力（テンプレート・原単位・推論ルール・判断）側を直して再生成する**。建物生成の運用（モデルを直接編集せず生成器／注釈を直す）と同型。

## 4. 完了条件（計画検証 PL ルール）

### 4.1 検証ルール

| # | ルール | 判定内容 |
|---|---|---|
| PL-01 | 概要整合 | `overview` の用途・構造・階数・面積・高さが建物モデルと一致する |
| PL-02 | ネットワーク閉合 | 全作業に先行・後続が繋がり（始端・終端を除く）、循環がなく、調達搬入→使用作業、検査→ゲート先作業まで到達できる |
| PL-03 | 数量カバレッジ | 建物モデルの全ての部材・室・設備系統が最低1つの作業の対象になっており、数量の二重計上・計上漏れがない |
| PL-04 | 日数根拠 | 全作業の日数が「数量÷（歩掛×投入数）」の式、または固定根拠（養生期間・検査リードタイム・製作期間）のいずれかで追跡できる。根拠のない日数は置けない |
| PL-05 | 暦整合 | 全体工程が暦展開済みで、終端日＝`premises` の推定工期（基準値）と一致する。閉所日・作業不能日に作業が置かれていない |
| PL-06 | ゲート完全性（普遍条件） | 隠蔽部の全件に「閉じる作業」より前の検査チェーン（書類→申請→実施）が接続し、法定検査・受電→試運転の順序が守られる。**この条件を満たさない計画では引渡しに到達できない**（本編の検査ゲート普遍条件と同一） |
| PL-07 | 仮設整合 | 各段階の仮設計画が当該段階の作業範囲を覆い、揚重機の能力（吊荷重×半径）が最大部材を満たし、置場容量が在庫ピーク以上ある |
| PL-08 | 資源競合の明示 | 労務・クレーン・ゲートのピーク競合が検出され、解消済みか `risks`/警告として明示されている（未検出のままの完了は不可） |
| PL-09 | 金額整合 | 作業原価の合計＝直接工事費、共通費を加えた総額＝推定工事価格と一致する。㎡単価が統計レンジから外れる場合は理由（グレード・地下・杭等の補正項目）が記録されている |
| PL-10 | 工期整合 | 推定工期が積み上げCP長と一致する。外部から目標工期が与えられた場合は工期率（目標÷推定）を算出して記録する（1.0未満＝圧縮が必要な計画として扱い、無言で短縮しない） |
| PL-11 | 段階整合 | 仮設の段階遷移（足場の組立→存置→解体、事務所・置場の移設、ゲートの切替）が工程と矛盾しない。解体済みの面で外装作業が残っていない |
| PL-12 | 判断の明示 | 全ての計画要素に根拠タグがあり、C層の判断は `decisions` に記録されている。建物側 `gap` 由来の要素が `rule` に格上げされていない |

### 4.2 完了レベル（決定）

- **L1 骨格完了**：PL-01〜PL-05, PL-07 を満たす。A層のみで到達可能。工法・判断に `default` が残ってよい。
- **L2 実施可能完了（＝計画完了）**：PL 全件を満たし、`undecided[]` が空。ゲーム開始の条件はこれ。
- **L3 承諾相当**：L2＋品質計画部分について所長確認を経た状態（実務の承諾に対応する定義として残す）。**（決定 DP-4、2026-11-10 訂正）ゲームではスキップする**（開始イベントとしては置かない）。ゲームの計画完了は L2 で確定する。

## 5. 前提推論の詳細（CP-0／CP-6）

### 5.1 数量エンジン（工期と金額の共通母数）

建物モデルの幾何から直接数えるものを本命とし、数えられないものだけ原単位（構造・用途別の係数テーブル、`default` タグ）で補う。

| 数量 | 算出元（建物モデル） | 方式 |
|---|---|---|
| コンクリート量 ㎥ | Slab（面積×版厚）、Foundation、柱・梁の断面×長さ | 幾何から直接 |
| 型枠量 ㎡ | Slab下面積、梁側面、柱周長×階高、基礎側面 | 幾何から直接（転用回数は別途 CP-4 で決める） |
| 鉄筋量 t | 配筋仕様文字列（Reinforcement.spec、例 D13@200）がある部材はそこから、無い部材はコンクリート㎥当たり原単位 | 直接＋原単位 |
| 鉄骨量 t | Column/Beam の本数×長さ×断面からの単位重量。断面が代表値のみの場合は延床当たり原単位で検算 | 直接（＋検算） |
| 掘削・残土 ㎥ | Earthwork（範囲×深さ） | 幾何から直接 |
| 山留め ㎡ | 掘削範囲の周長×深さ | 幾何から直接 |
| 外壁・仕上面積 ㎡ | Wall 長さ×階高、Room 面積（床・天井）、Roof 面積 | 幾何から直接 |
| 設備量 | Shaft 数、Room 用途別器具数、EquipmentRun 長さ（未生成時は系統テンプレートで推論、§5.4） | 直接＋推論 |
| 杭 | Foundation.piles の規則（柱位置・本数）。長さは groundAssumption 由来で `inferred` | 規則＋推論 |

### 5.2 工期推論（決定：積み上げ方式、3点推定）

```
推定工期（暦日） ＝ 準備期間 ＋ 本体期間（暦展開したクリティカルパス長） ＋ 後片付け・検査引渡し期間
作業日数（実働） ＝ 数量 ÷（歩掛 × 投入数）　※固定型（養生・乾燥・検査・製作）は根拠付き固定日数
暦展開：実働日数を calendarProfile（4週8閉所・祝日・長期休暇）と weatherProfile（工種別作業不能日）で暦に変換
```
- 躯体の積み上げ単位（実務）：S造は**節**（2〜3階分を1節。建方→本締め・建入れ直し→デッキ→床配筋→打設）、RC造は**フロアサイクル**（墨出し→配筋・型枠→仕込み→検査→打設→養生→脱型）。公的な一律日数はなく、養生の下限（湿潤養生：早強3日／普通5日／中庸熱等7日以上 等の品質条件）がサイクルの下限を決める。
- **本プロジェクトの確定ルールが実務一般に優先する点**：躯体（建物全体の鉄骨フレーム＋床スラブ）が完了するまで、外装・設備・内装は開始しない（先行の打込み＝スリーブ・インサート・埋設配管のみ例外）。実務調査の「躯体（上階）×内装・設備（下階）」ラップは採用しない（WORK_STRUCTURE_V2 §8、ユーザー確定 2026-11-09）。ラップは躯体内部の工区追っかけと、躯体完了後の外装・内装の工区／面ラップに限る。
- 3点推定：低＝歩掛・投入数が favorable、作業不能日少なめ／基準＝標準値／高＝歩掛悪化・作業不能日多め・検査是正1回分を含む。幅そのものがリスク情報として `premises` に残る。
- 検算：工期率（外部目標がある場合）と、階数・延床からの粗いレンジ照合。外れた場合は「どの段の積み上げが原因か」を返す（単純式で上書きしない）。

### 5.3 金額推論（決定：積み上げ＋㎡単価照合）

```
直接工事費 ＝ Σ（工種別数量 × 単価〈複合単価・市場単価相当のゲーム用テーブル〉）
純工事費 ＝ 直接工事費 ＋ 共通仮設費（率または積み上げ）
工事原価 ＝ 純工事費 ＋ 現場管理費（率または積み上げ）
工事価格 ＝ 工事原価 ＋ 一般管理費等
実行予算 ＝ 工事原価ベースに companyPolicy（本社・支店の査定）で設定。請負金額−実行予算＝見込粗利
```
- 検算レンジ（建築着工統計由来、2024年・工事費予定額ベース）：事務所 456.3千円/㎡、店舗 250.9千円/㎡、工場 367.6千円/㎡、非住宅計 338.8千円/㎡ (実務)。**店舗平均はテナント内装を含まない物件に引きずられた値で、大規模商業施設の推定にそのまま使わない**（PL-09 の補正理由の記録で対応する）。
- 補正項目（±の理由として列挙する）：地下の有無、杭・山留め、地盤、グレード（外装・設備）、狭小敷地・搬入制約、時点補正（物価指数）。
- 精度の段階づけ（実務）：企画＝㎡単価法 → 基本設計＝部位別概算 → 実施設計＝精積算。本生成は「基本設計〜実施設計の間」に相当し、数量が幾何から数えられる分だけ㎡単価法より細かい、と位置づける。

### 5.4 EquipmentRun 未生成への対処（決定）

シード建物では設備の横引きが未生成（既知の gap）。計画側は `systems`（受電方式・給排水・空調・熱源・EV・火報）と Shaft 配置から系統テンプレート（受電→電気室/EPS→縦ラック→各階分電盤、PS縦管→横引き分岐 等、WORK_STRUCTURE_V2 の天井裏順序を含む）で EquipmentRun 相当を推論生成し、全要素に `inferred` タグを付ける。モデル側で正式生成されたら差し替える（本編3Dの暫定表現→正式データ差し替えと同じ運用）。

## 6. 推論ルール（B層）の要点

### 6.1 工法選定の候補生成と初期値

| 論点 | 候補生成ルール（入力→候補） | 初期値の置き方 |
|---|---|---|
| 山留め | 掘削深さ×地盤×隣地近接 → 親杭横矢板／SMW／地中連続壁（地下水位高では止水級が必須、PARAMETER_DESIGN P7 と同規則） | 深さ・止水条件を満たす最小級 |
| 杭・基礎 | groundAssumption（支持層・液状化）＋ seedSpec.foundationType（あれば確定） | シード優先、無ければ地盤仮定から |
| 揚重 | 高さ・最大部材重量・平面の広さ → ラフター＋横引き（原則）／タワー1基 | **確定ルール：タワーは最大1基・基礎完了後・盛替え有償。複数基の同時計画は禁止**（ユーザー確定） |
| 足場 | 高さ・外装工法 → 枠組／くさび／ゴンドラ併用（高層） | 面別に組立→存置→解体を生成 |
| 打設 | 1回打設量×ポンプ能力 → ポンプ圧送（標準）／バケット | 工区あたり打設量から |
| 工区数 | 階面積と1日打設可能量・揚重能力から推奨数を算出 | 建物モデルの Zone が既にあればそれを採用（生成済み物件では Zone が正） |

比較スコアは {工期, 原価, 安全, 近隣影響, 施工性} の5軸で出し、`methods` に候補ごと保存する。初期採用はスコア最大ではなく「制約を満たす中で標準的なもの」とし、攻めた選択（ラップ拡大・PCa化等）は C層の判断に回す。

### 6.2 ラップ可否の初期判定

可否は4条件（物理的干渉なし／品質条件〈養生・乾燥〉を侵さない／検査を飛ばさない／安全が分離できる）で判定する (実務)。ただし §5.2 の確定ルールにより、躯体完了前の外装・設備・内装の開始は条件以前に不可とする。

### 6.3 WBSテンプレート

- テンプレートの軸は `構造（S/RC/SRC）×工法（在来/PCa）` で躯体部分が全面的に切り替わり、仕上・設備部分は用途で切り替わる（PARAMETER_DESIGN 第3・4群の切替表を正とする）。
- 既存の実体：S造・商業＝WORK_STRUCTURE_V2（土工→基礎→鉄骨節→外装レーン→設備3系統×3段階→内装チェーン→EV単独レーン→屋上→外構→検査群 自→監→施→法）。他構造・他用途はテンプレート追加として扱い、無い組み合わせは生成を止めて `gap` を返す（黙ってS造テンプレートを流用しない）。

## 9. ゲームへの接続メモ

- 生成された全体工程が、本編の「全体工程は着工時点で出来上がっている」という既存前提の**生成根拠**になる（従来は前提として置いていたものが、建物モデルから導出されるようになる）。
- 3ヶ月工程（所長＋課長）と1ヶ月工程（担当者作成→課長チェック）は、全体工程からのローリング詳細化として施工中に生成する。初期計画の `schedules` に初回窓の骨格だけ含めるのはその接続のため。
- 計画と実績の差分が施工中の立て直し（応援・残業・工順変更・挽回計画）の入力になる。計画側は差分を検出できる粒度（作業×日×原価）で出すことが要件で、それ以上の介入はしない。
- 実行予算は QCDSE の C（本社・支店が設定し現場が達成する）の数値根拠になる。`premises` の実行予算と照合結果が、C の初期値と「無理な予算かどうか」の演出根拠を兼ねる。
- 実装状況（2026-11-10）：DP-2 テーブル（`model/cost_tables.json`）と CP-0 試作（`model/plan_cp0.py`）に続き、CP-1〜CP-10 の生成パイプライン（`model/plan_generate.py`）が動作し、ゲーム物件・蘇我・亀有の3物件で ConstructionPlan 全12ブロック（タスク217〜286件・検査チェーン22〜29件・暦日付・Sカーブ・調達期限つき）が生成され、計画検証 PL-01〜PL-12 は3物件とも全件 PASS（難易度 hard でも PASS を確認）。詳細と検証の経緯は `model/COST_TABLES.md` と `model/PLAN_PIPELINE.md`。その後、統合手前まで完了：設備推論（equipment_infer.py、F-02 は inferred 化）、山崩し提案とローリング詳細化（plan_postprocess.py、3ヶ月／1ヶ月工程を生成）、統合手前パッケージ（integration/PLAN_TO_GAME.md＋plan_to_game.py、ゲーム物件は全52ゲーム日に変換検証 PASS）。残りは本編への統合のみ（メイン側の判断事項）。ここまでの全手順はスキル `construction_plan_generation`（~/workspace/custom-skills/）に明文化した。
