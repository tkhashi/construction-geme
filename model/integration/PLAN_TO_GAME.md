# 工事計画 → 本編ゲーム 接続仕様（統合手前パッケージ）

作成：2026-11-10（サイドチャット「建築 工事 計画 手順 調査」）。本編への統合そのものはメイン側の判断事項であり、ここは「統合するならこの形で渡す」という手前までの成果物。変換器は `model/plan_to_game.py`。

## 1. 渡すもの

| 計画側（生成物） | 本編側での受け方（想定） | 備考 |
|---|---|---|
| `generated_construction_plan_*.json` の tasks | ゲームのタスクマスタ（全体工程の生成根拠） | 本編の「全体工程は着工時点で出来上がっている」という前提の生成根拠になる |
| tasks の deps（finish-start／gate／resource） | 前後関係とゲート | gate は検査チェーン完了が後工程の開始条件（引渡しの普遍条件と同一） |
| inspections（書類→申請→実施） | 本編の検査チェーン仕様（WORK_STRUCTURE_V2 §3）と同型 | 申請期限は plan_postprocess のローリング出力にも入る |
| premises（数量・原価・実行予算・3点推定） | C（原価）の初期値と「無理な予算か」の判定材料 | 実行予算が QCDSE の C の数値根拠 |
| meta.difficulty / seed、decisions | ゲーム開始パラメータ | 難易度はユーザーが選ぶだけ、実値はシード抽選済み（DP-3） |
| schedules.sCurve | 出来高・予実管理の基準線 | 月次 |
| generated_plan_detail_*.json（3ヶ月／1ヶ月） | ローリング工程の初期窓と担当者TODOの種 | 3ヶ月＝所長＋課長、1ヶ月＝担当者作成・課長チェックの役割分担を含む |

## 2. 日数換算（DP-1）

- 計画は実日数（実働日）で保持するのが正。ゲーム日数への換算は本変換器（表示・進行層）で行う。
- 換算パラメータ `durationScale`（実働日／ゲーム日）。既定は **7**。根拠：ゲーム物件の計画実働 362日 ÷ 7 ≒ 52ゲーム日となり、本編の既存バランス（計画43日・期限54日・能動プレイ完了52〜54日）と同程度の物量になる。バランス調整はこの値だけで行う。
- 変換規則：gameStart = floor（実働ES ÷ scale）＋1、gameEnd = ceil（実働EF ÷ scale）。依存の単調性（後工程のゲーム日が前工程より後ろになること）は変換器が検証する。

## 3. 変換器の出力と検証

- 出力：`model/integration/generated_game_schedule_<name>.json`（タスクのゲーム日・ゲート・検査チェーン・前提数値・難易度/シードを格納）
- 検証（変換器内蔵）：ゲート先タスクの存在、依存の単調性、最終ゲーム日 ＝ ceil（総実働 ÷ scale）、検査チェーンの3段が揃っていること。落ちたら変換器の入力（計画生成側）を直す。

## 4. メイン側で決めること（未決定として明示）

- 本編の予算単位への換算（計画は円で渡す。ゲーム内ポイントとの対応はメイン側のバランス設計）
- 計画タスク（286件規模）と本編タスク（215件規模）の粒度の対応付け：そのまま置き換えるか、計画を「全体工程の根拠」として保持し本編タスクへ射影するか
- ローリング詳細化（3ヶ月／1ヶ月）を本編の工程表作成タスクとどう接続するか
- 難易度選択を開始フロー（物件ランダム選択）のどこに置くか
